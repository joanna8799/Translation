# 小說：來源、做法、成本模型

小說比漫畫簡單，因為大多數情況不需要 OCR、不需要找氣泡、不需要擦字。
但小說的文字量是漫畫的十倍以上，所以額度不能用「頁數」計，要用「token 數」計。

## 1. 小說有三種來源，做法各不同

| 來源 | 例子 | 文字在哪 | 做法 | 難度 |
|---|---|---|---|---|
| 網頁小說 | 小説家になろう、カクヨム、Alphapolis、Pixiv 小說、문피아、네이버 시리즈（網頁版）、起點 | DOM 文字節點 | 瀏覽器擴充直接翻文字，雙語對照或整段替換。沈浸式翻譯的本業。 | 低 |
| App 內小說 | Kakao Page、Naver Series、Piccoma、LINE Manga 小說區、Ridibooks | 畫面上渲染的文字，多半不可選取 | Android：AccessibilityService 讀 UI 樹上的文字節點，讀不到再退到螢幕擷取加 OCR；iOS：截圖捷徑或自家閱讀器 | 中 |
| 檔案 | EPUB、TXT、PDF、使用者貼網址 | 檔案內 | 自家 app 內閱讀器，逐段翻、逐章翻 | 低 |

### 網頁小說（瀏覽器擴充）

- content script 找出正文容器（多數小說站是一個大 `<div>` 或 `<p>` 序列），把段落切成 chunk，捲到哪翻到哪。
- 兩種顯示：原文下方插入譯文（雙語對照，沈浸式翻譯預設），或整段替換並保留「顯示原文」切換。
- 免費層可以直接用 Chrome 內建 Translator API（桌面），完全不花錢。
- 不需要網站白名單。通用的「找正文」規則（最長文字區塊）對九成小說站有效，剩下的做少量站點適配。

### App 內小說（Android）

- 第一條路：AccessibilityService。很多閱讀 app 用原生 TextView 渲染，無障礙服務可以直接讀到文字，不用擷取螢幕，也不用 OCR，速度快、零誤字。
- 第二條路：MediaProjection 螢幕擷取加 ML Kit OCR。用在 WebView 或自繪 canvas 的閱讀器。純文字 OCR 比漫畫字型準很多，ML Kit 端側就夠。
- 顯示：整頁翻譯面板蓋在畫面上，或半透明對照。小說不需要就地排版，體驗比漫畫容易做。
- Play 商店對 AccessibilityService 的用途審核嚴格，要在上架說明裡講清楚是給使用者翻譯畫面文字用。

### App 內小說（iOS）

- 跟漫畫一樣，iOS 不允許讀其他 app 的畫面。可行的只有：截圖捷徑（截圖後 Vision OCR 再翻，任何 app 都適用）、Safari 擴充（網頁版小說）、自家閱讀器（貼網址或匯入檔案）。
- EasyComix Pro 的「網路小說翻譯，每日更新章節」推測就是自家閱讀器：使用者貼小說網址，app 抓章節、翻譯、每天追更。這對 iOS 是最合理的做法。
- PiP 字幕條不適合小說，長文字塞不進去。

## 2. 成本模型：一章小說是一頁漫畫的十倍以上

假設一章日文或韓文網路小說約 3,000 到 6,000 字，取 5,000 token 輸入、3,500 token 輸出（中文譯文）。

| 模型 | Input US$/M | Output US$/M | 每章 | 每天 10 章、一個月 300 章 |
|---|---|---|---|---|
| Gemini 2.5 Flash-Lite 級（第三方整理，請以官方為準） | 0.10 | 0.40 | 0.0019 | 0.57 |
| Claude Haiku 4.5 | 1.00 | 5.00 | 0.0225 | 6.75 |
| Claude Sonnet 5 | 2.00 | 10.00 | 0.045 | 13.5 |
| Claude Opus 5.5 | 4.00 | 20.00 | 0.09 | 27 |

對照漫畫：重度用戶每月 1,800 頁用 Sonnet 5 約 US$7.4。小說重度用戶用同一個模型是 US$13.5，超過 US$4.99 的月費。

所以小說的 Pro 方案必須：

1. **額度用 token 計，不用章或頁計。** 沈浸式翻譯 Pro 給每月 20M token，就是這個原因。
2. **Pro 預設走便宜模型。** Haiku 4.5 或 Flash-Lite 級當預設，每月 5M token（約 600 章）成本 US$1 到 6，訂閱費蓋得住。
3. **高品質模式扣額度更快。** 切到 Sonnet 5 時同一章扣 3 到 4 倍額度，讓使用者自己選要品質還是要量。
4. **免費層走端側翻譯，無限。** Chrome Translator API、ML Kit、Apple Translation 翻小說的品質是「看得懂」，不是文學等級，但對追更夠用，而且成本為零。
5. **整本預翻走 Batch API。** Anthropic 的 Message Batches 是標準價的一半，適合「把這本書後面 200 章一次翻完」這種不急的需求，鎖在 Pro。

## 3. 小說專屬的省錢手法

1. **章節共享快取效果比漫畫更好。** 網頁小說有穩定的 URL，key 用「網址加正文雜湊加目標語言加模型層級」，熱門作品第二個讀者起全部吃快取。
2. **只翻看得到的段落。** 捲到哪翻到哪，預翻下一屏就好。一章看一半關掉的人很多。
3. **詞彙表與人名表放在快取前綴。** 用 prompt caching，每章只有正文是新的 token。人名、地名、專有名詞一致性也靠這個。
4. **控制輸出長度。** 中文譯文通常比日文原文短，不要讓模型加註解或說明，structured output 只回譯文。
5. **段落級快取。** 同一章重新整理或換模型時，沒變的段落不重翻。

## 4. 翻譯品質上小說跟漫畫的差別

- 漫畫是短句加上下文靠畫面，LLM 的優勢在「語氣」與「口語」。
- 小說是長文，LLM 的優勢在「人名一致」、「敬語與稱謂」、「上下文指代」。這些靠詞彙表與前幾章摘要放進 prompt 來維持，正好可以用快取前綴，不會增加太多成本。
- 端側翻譯引擎最大的弱點就是人名與稱謂不一致，所以「免費層看得懂、Pro 才順」是自然的分層。

## 5. 對現有架構的影響

- 雲端 proxy 不變，只是請求格式多一種：`{ "kind": "text", "chunks": [ { "id": 0, "text": "..." } ] }`。
- 額度系統從「每日頁數」改成「每月 token 數」，漫畫也一併換算成 token（一頁約 300 到 800 token），兩種內容共用一個額度。
- 瀏覽器擴充在 Phase 1 就能順便支援網頁小說，因為文字翻譯比漫畫簡單，幾乎是免費附送。
- Android 多一個 AccessibilityService 路徑，適合放在 Phase 3。
- iOS 自家閱讀器加「貼網址追更」功能，放在 Phase 4。
